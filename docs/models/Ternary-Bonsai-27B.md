# Ternary-Bonsai-27B
> Extracted verbatim from AGENTS.md on 2026-08-15. "Above/below" references may point
> to sibling files in this directory or back to AGENTS.md.

Ternary Bonsai 27B (Prism ML, Apache-2.0, ternary quant of Qwen3.6-27B): dense 27B, arch `qwen35`, 65 layers, native 262144. End-to-end **ternary** weights ({-1,0,+1}) at a true 1.71 bpw, 7233 MiB on disk — a third of what the other 27B-class models here cost, and the card claims 94.6 % of FP16 quality (80.49 vs 85.07 across 15 thinking-mode benchmarks) against 85.5 % for a conventional IQ2_XXS build. **Pick the right pack**: the repo ships three 2-bit files and only one works on stock llama.cpp. `Ternary-Bonsai-27B-Q2_0.gguf` is g128 and needs Prism's own fork (the card's quickstart clones it); `Ternary-Bonsai-27B-Q2_g64.gguf` is the group-64 pack the card describes as "matching the 64-value-group Q2_0 packing in llama.cpp", and build 10243 loads it in 3.3 s with no errors — verified 2026-08-05. `PQ2_0` is a third variant the card never explains and was not tried. **Measured on hermine 2026-08-05** at `ctx-size = 262144`, `fit = off`: KV `q8_0`/`q8_0` gives **18663 MiB of 23028** (4365 MiB free), KV `q4_0`/`q4_0` gives 14590 MiB (8438 free) — and both run **70.0-70.3 t/s generation** / ~3120 t/s prompt, i.e. the KV type is free here. The presets therefore use `q8_0` on hermine and keep the Vulkan `q4_0` floor in the example, even though the card standardizes on a 4-bit KV cache: that recommendation exists to fit laptop memory budgets, and on a 23 GB card the better cache costs nothing measurable. **DSpark is out, and the reason is a repo policy rather than a dead end.** The card ships a DSpark drafter and advertises a lossless 1.34x CUDA decode speedup at draft depth 4; `llama-server --spec-type` on build 10243 even lists `draft-dspark`. It cannot work here, and the investigation on 2026-08-05 went three layers deep before that was certain. First the drafter failed to load with `gguf_init_from_reader: tensor 'dspark.fc.weight' has offset 337718592, expected 357584192` — 19865600 bytes, exactly 1 byte per 64-element block. The file was **not** at fault: byte-complete at 1946393568 bytes, header declaring `general.architecture = dspark` and `dspark.block_count = 6`. The cause is that the two shipped files pack the *same* ggml type 42 differently, and each toolchain says so itself — the Prism fork documents `Q2_0 : 2.125 bpw` (17 bytes/block), upstream documents `Q2_0 : 2.25 bpw (group 64)` (18 bytes/block). Hence the mirrored errors: upstream rejects the drafter, and the fork rejects the `Q2_g64` main model with `'output_norm.weight' has offset 357580800, expected 337715200`. Repacking the drafter (recomputing offsets and substituting the target's correctly packed `token_embd.weight`, which the card says the drafter shares anyway) fixed the container — every offset then matched — and revealed the real wall: `unknown model architecture: 'dspark'`. **Upstream does not implement the dspark architecture at all**; the flag exists in the argument parser only. Release b10297 (2026-08-06) mentions it zero times. The only working combination is the Prism fork plus the g128 `Ternary-Bonsai-27B-Q2_0.gguf`, and the fork does publish prebuilt Windows CUDA-12.4 binaries, so no compiler would be needed — but **this repo uses official llama.cpp builds only** (see Conventions), so that path is closed by choice, not by capability. The section therefore runs `ngram-mod`. Do not re-litigate this without first checking whether an official release has added the `dspark` arch; the drafter GGUF and the `models.list` line for it have been removed. Vendor sampling: `temp 0.7`, `top-p 0.95`, `top-k 20` (the settings behind all reported thinking-mode numbers). Vision is available via an optional mmproj (629 MB `Q8_0`), not downloaded, so the preset is text-only. llama.cpp reports `chat template supports preserving reasoning` here as it does for Ornith; the card documents neither preserved thinking nor a system prompt beyond "You are a helpful assistant", so no `reasoning = on`.
