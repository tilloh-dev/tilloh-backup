# Nemotron-3.5-Lightning-30B-A3B
> Extracted verbatim from AGENTS.md on 2026-08-15. "Above/below" references may point
> to sibling files in this directory or back to AGENTS.md.

Nemotron-3.5-Lightning-30B-A3B (NVIDIA, OpenMDW-1.1, agentic reasoning/chat): 30B-A3B MoE, arch `nemotron_h_moe`, **53 layers of which only 7 carry attention** (`attention.head_count_kv` is a per-layer list reading 2 for seven layers and 0 for the other 46), the rest being Mamba-2 SSM layers with constant-size recurrent state. 128 experts, 6 routed + 1 shared active, native `context_length = 1048576`. That layout is the whole story of this section: `llama-fit-params` puts the KV cache for the **full 1M context** at 3311 MiB, so context is nearly free and VRAM is spent on weights instead.

**The URL this work started from was the wrong checkpoint, and the difference is not cosmetic.** `nvidia/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-Base-BF16` is the *base* checkpoint — the card says "no supervised fine-tuning, reinforcement learning, or distillation has been applied". No chat template, no tool calling, and no MTP drafter GGUF exists for it (only `mradermacher` quantizes it at all). The post-trained `…-30B-A3B-BF16` is what this section serves. If a future reader follows the Base link, that is why it was not used.

**Quant choice is forced by a tensor shape, not by taste.** `expert_feed_forward_length = 1856`, which is **not a multiple of 256**, so every K- and IQ-superblock type (256-element blocks) is unrepresentable on the expert tensors and llama.cpp falls back to a 32-element-block type. The experts are 15758 MiB of the 18046 MiB file, which is why the whole quant ladder collapses onto one size: bartowski's IQ2_XXS is 17965 MiB and IQ4_NL is 18046 MiB — **81 MiB apart**, while Q4_1 jumps to 19905 MiB and Q4_K_S to 23.20 GB. Everything below IQ4_NL is therefore *strictly dominated*: same size, worse weights. Verified by parsing the GGUF tensor table — in the IQ4_NL file the experts land on `IQ4_NL` (46 tensors) with 2 on `Q4_0`, i.e. the best 4-bit 32-block type available. `bartowski` over `unsloth` because unsloth ships no MTP sidecar at all; that turned out not to matter (see below) but was not knowable in advance.

**The MTP drafter is a large net loss and is deliberately not wired.** This is the opposite of every other MTP section in this file. Measured 2026-08-15 on hermine, build 10424, ctx 131072, KV `q8_0`/`q8_0`, `fit = off`: with `model-draft = mtp-…-Q8_0.gguf` + `spec-type = draft-mtp,ngram-mod` the load sits at **22303 MiB and generates 86.7 t/s**; dropping the drafter gives **19054 MiB and 195.1 t/s**. That is **3249 MiB** of VRAM — far more than the drafter's 2075 MiB file, because it allocates its own context — bought at **2.25× slower generation**. Draft acceptance was not the problem (0.723 at ctx 262144, mean length 3.87 against a budget of 4, i.e. the budget was nearly saturated). The mechanism is that the target is an A3B MoE with only ~3B active parameters while the MTP block is a ~2 GB dense model, so a drafter forward pass costs roughly what a target forward pass costs and speculation cannot win. Confirmed at three context points with the drafter (86.7 / 105.4 / 95.7 t/s at 131072 / 196608 / 262144) against three without (195.1 / — / 175.1). **Do not re-add `draft-mtp` here without re-measuring**; this paragraph claimed a `# NOTE` in both preset files points here, and the note's absence is now explained: the user deletes comments from `models.ini` deliberately (see the comment-policy bullet under llama.cpp config notes), so warnings must live here and in `models.example.ini`, never in `models.ini`. Also recorded so nobody repeats it: bartowski's `mtp-…-Q4_0.gguf` **fails to load outright** (`failed to load draft model`) while the Q8_0 one loads, cause not investigated because the feature was being dropped anyway.

**`ctx-size = 262144`, chosen against a measured 524288.** Real loads without the drafter: 131072 → 19054 MiB (3974 free) / 195.1 t/s, **262144 → 19985–20476 MiB (3043 free) / 175.1 t/s**, 524288 → 21518 MiB (1510 free) / 163.6 t/s. The full native 1048576 does not fit (`llama-fit-params` 22530 MiB plus a ~1172 MiB desktop baseline exceeds 23028). 524288 would have hit this repo's stated ~1.5 GiB headroom target exactly and was rejected on the repo's other rule, "throughput beats context": it taxes every generated token by 6.6 % to buy a window that also sits outside NVIDIA's own validated envelope (the card validates 256K on a single H100 and reports RULER 256K 76.88 against RULER 1M 69.62). There is **no throughput cliff** in this range, unlike Ornith-1.0-35B — the degradation is smooth. `fit = off` is a no-op as measured and is set only so a future shortfall fails loudly.

**Compute buffers do not grow with prompt length here, which is worth knowing because the Muse-Glimmer section was burned by assuming they might.** A 141389-token prompt at ctx 524288 measured 21471 MiB peak against 21522 MiB idle — i.e. *nothing*; at 262144 it was 20476 against 20269, +207 MiB. Prompt throughput on that real prompt is 6567–7004 t/s and generation at 141k of context still 102.8–111.1 t/s. The 30-token probes used elsewhere in this file report prompt throughput as 80–225 t/s and are pure noise; ignore them.

Sampling is one published set and the GGUF agrees with the card: `general.sampling.temp = 1.0` and `general.sampling.top_p = 0.95` are baked into the file's metadata, and **no `top_k` is published**, so none is set — do not import the `top-k 20` from the neighbouring Qwen sections. Thinking is **on by default and verified rather than assumed**: the embedded template reads `enable_thinking = enable_thinking if enable_thinking is defined else True`, so unlike Laguna no explicit `reasoning = on` is needed, and `jinja = true` + `reasoning-format = auto` suffice. The template also consumes `reasoning_content` from history and llama.cpp suggests `--reasoning-preserve`; not set, following the Ornith precedent that the card must confirm it. **The card's coding-agent advice does not apply to this GGUF**: it tells agents to send `chat_template_kwargs: {"force_nonempty_content": true}`, but that key does **not exist** in bartowski's embedded template (checked), so setting it would be a silent no-op. `cache-ram = 16384` matches hermine's other agentic sections. `spec-type = ngram-mod` is kept — no draft model, no VRAM, lossless — but its value here is **unmeasured**: the A/B run was started and aborted, so this is the same mechanism-only assumption as every other section, not a measurement.
