# Muse-Glimmer-30B
> Extracted verbatim from AGENTS.md on 2026-08-15. "Above/below" references may point
> to sibling files in this directory or back to AGENTS.md.

Muse-Glimmer-30B (Meta, Apache-2.0, agentic multimodal): dense 29.6B, arch `muse-glimmer`, 52 layers, native 131,072 context. Hybrid attention `[Local, Local, Local, Global]` repeating with sliding window 2048, so only 13 of 52 layers carry a growing KV-cache (2 KV heads, head dim 128, GQA 16:1). `kquant-17gb` is 15980 MiB on disk, the vendor's own 24 GB target (a `kquant-dynamic` at 19.7 GB targets 32 GB and is not downloaded). Card puts the quantization cost at 1.0 % averaged over 15 benchmarks against full precision.

**The arch landed between two builds on the same day, so read version numbers here carefully.** b10344 (newest release for most of 2026-08-10) rejects `unknown model architecture: 'muse-glimmer'`: PR #26841 merged as commit `62bf73d` at 11:07 UTC, while b10344 targets `7a20b417f` from 08:25 UTC. Upstream says the same in issues #26858 and #26865, and the "the ROCm build works" claim in #26865 was retracted by its own reporter — the arch check is backend-independent frontend code, so no b10344 asset can load it. **b10353 (`f8def7fe1`) does contain it**, and `server.sh`'s auto-update pulled that build the same evening, which is when everything below became measurable. If a preset here ever fails with the arch error again, check `llama-server --version` before anything else.

**Measured on hermine 2026-08-10, build b10353, `ctx-size = 131072` with the mmproj resident on the GPU:** **21717–21726 MiB of 23028**, i.e. **882–892 MiB free** across three stable samples. The previous configuration (`ctx-size = 65536`, mmproj offloaded to host RAM) measured 19575–19619 MiB with 2990–3453 MiB free. Both were real loads with all three stages up — the router log shows `text_model`, `spec_model` and `mmproj_model` each reaching 1.0, and `/props` on the child reports `n_ctx = 65536`/`131072` and `"vision": true`. Note that **router mode suppresses llama.cpp's own `llama_kv_cache` and buffer-size lines**, forwarding only load-progress state, so the per-buffer breakdown is *not* available this way; the VRAM total is the authoritative figure and a single-model run would be needed to itemise it.

**The 892 MiB margin is a deliberate, informed choice and thinner than this repo's own guidance.** The working target elsewhere in this file is ~1.5 GiB, and 131072 was picked over 98304 (~1.1 GiB free, projected) and over moving the mmproj back to host RAM (~2.2 GiB free, projected) with the risk accepted explicitly: a single image can carry up to 4096 visual tokens and allocates vision compute buffers at request time, which is exactly what this margin has to absorb. If image-heavy use ever OOMs, set `mmproj-offload = false` first — that is the cheapest lever and it keeps vision working.

**A KV-per-token estimate got this wrong by ~700 MiB, which is why the number above is a load and not a calculation.** The estimate reasoned that only 13 of 52 layers are global and therefore grow with context (2 KV heads × 128 head dim at `q8_0` ⇒ ~6.9 KiB/token, 926 MiB at 131072) and projected ~1600 MiB free with the mmproj resident. Actual: 892. The 13-global-layer model itself is sound and was confirmed the other way round — at 65536 the whole KV+compute bucket measured ~1030 MiB, whereas allocating full context on all 52 layers would have needed 1.85 GiB of KV alone, so the sliding-window optimisation is provably active. What the estimate missed is that a resident mmproj costs materially more than its 1335 MiB file and that compute buffers grow with context.

**What was verified before the arch existed**, and is worth keeping because it isolates key-name validity from arch support: on b10344 the router loaded all 10 custom presets, `/v1/models` listed `Muse-Glimmer-30B`, and a chat request failed with *only* `unknown model architecture` — no argument or flag error anywhere. So every key name in the section is accepted, including `mmproj-offload`, `cache-type-k/v-draft`, `cache-ram` and `spec-type = draft-dflash,ngram-mod`.

**`spec-draft-n-max = 16`, not the 4 this repo uses everywhere else.** That 4 was inherited from the MTP sections and is wrong here on the vendor's own numbers: DFlash is a block-diffusion drafter that "predicts entire blocks of 16 tokens in a single forward pass", so a budget of 4 discards 12 of every 16 drafted tokens and caps the advertised 3.1× speedup (RTX 5090, 74.9 → 233.4 t/s). `--help` reports the flag's default as 3, which is tuned for one-token-per-head MTP drafters and is equally wrong for a block drafter. 16 is mechanism-derived, and the **measurement on 2026-08-10 vindicates the direction without reaching the value**: mean accepted draft length is **6.03–6.17** at short context (acceptance 0.337–0.344), so the inherited 4 would provably have clipped it, while 16 is never approached — the binding constraint is acceptance, not the budget. **Acceptance collapses with context length**: 0.34 / mean 6.17 at ≤2.2k tokens, 0.129 / mean 2.93 at a 31.6k prompt, 0.098 / mean 2.47 on a long mixed task. Generation tracks it — **128.2 t/s** at ~70 tokens of context, 117.0 at 2.2k, 55.5 at 31k, 46.5 on the long task — against a prompt throughput of 2400–2550 t/s throughout. So the card's 3.1× headline (RTX 5090, 74.9 → 233.4 t/s) describes short-context behaviour; do not expect it to survive a full agent context on this box.

**`cache-type-k/v-draft = q4_0` matters here, unlike the MTP sections.** The gemma-4-31B measurement below found the draft cache types save no VRAM at all, because an MTP drafter shares the target's KV cache. DFlash does not — it is a separate model behind `model-draft` with its own attention (sliding window 2048 over all layers, 32 query / 8 KV heads, sequence length 131072), and `--help` puts the draft cache default at **f16**. Quantizing it should therefore save real VRAM rather than nothing. Both are set to the same type because the CUDA matched-pair rule presumably applies to the drafter's fused kernel too (untested), and `q4_0` rather than `q8_0` because speculative decoding is lossless: a worse draft cache can only lower the acceptance rate, never corrupt output, which is the right way to spend a tight budget.

**The mmproj stays resident on the GPU, and the reasoning that first said otherwise was wrong.** Vision needs `mmproj-kquant.gguf` (1335 MiB, ViT-G/14 perception encoder) and `--mmproj-offload` defaults to *enabled*, i.e. in VRAM, so no key is set. The section originally carried `mmproj-offload = false`, argued from a loose anchor: file sizes sum to 15980 + 1555 + 1335 = 18871 MiB of 23028, and the only measured comparable was gemma-4-31B, which peaks at 22467 MiB with 560 MiB free at ctx 65536 while carrying ~1.3 GB *fewer* weights. That anchor pointed the right way about *cost* but the wrong way about *feasibility*: Muse-Glimmer's KV is far cheaper per token, so the real load at 131072 with the projector resident fits at 892 MiB free. Dropping `mmproj` entirely, as the other VLM sections here do, would free the same VRAM and lose vision outright; that was considered and rejected, and unlike those sections the file is actually on disk here.

`cache-ram = 16384` is set, matching hermine's other agentic-coding sections — the card's intended use is explicitly coding agents and long-horizon tool use. Embedded template consumes `reasoning_content` from history (preserved thinking), so `reasoning-format = auto` + `jinja = true`; **no `reasoning = on`**, because unlike Laguna the template was not found to default thinking off, and the card controls effort through the *system prompt* instead (`Reasoning strength: low|medium|high|xhigh`, "use high or xhigh for complex problem solving, coding, and agentic tasks"). That is a client-side string, not a preset key — OpenCode has to send it, and nothing in this repo does yet. Vendor sampling is one single published set, `temp 1.0`, `top-p 0.95`, `top-k 64`, adopted whole. `ngram-mod` is chained after `draft-dflash` for consistency with every other section, but note the interaction is **unexamined**: llama.cpp hardcodes all `ngram-*` ahead of all `draft-*`, so ngram-mod preempts the DFlash block draft whenever it finds a ≥48-token verbatim chain, and it also raises the global draft budget to 64. On a model whose headline feature is the DFlash speedup that could help or hurt; nobody has looked.
