# gemma-4-31B
> Extracted verbatim from AGENTS.md on 2026-08-15. "Above/below" references may point
> to sibling files in this directory or back to AGENTS.md.

Gemma 4 31B (Google/unsloth, Apache-2.0, dense QAT VLM): dense 31B (arch `gemma4`, 60 layers, native 256K ctx). Hybrid attention interleaves local sliding-window (1024) layers with periodic global layers (unified K/V + Proportional RoPE), so the growing KV-cache lives only in the few global layers → long contexts are cheap on VRAM. Quantization-aware-trained `UD-Q4_K_XL` (17.3 GB) keeps near-bf16 quality and fits a 24 GB card alongside the ~280 MB MTP drafter `mtp-gemma-4-31B-it.gguf`. MTP speculative decoding is wired via `spec-type = draft-mtp` + `model-draft = …/mtp-gemma-4-31B-it.gguf` (lossless — the target verifies every drafted token). Presets differ per machine: **lieselotte** (7900 XTX, Vulkan) `device = Vulkan0`, `ctx-size = 163840`, KV `q8_0`/`q4_0`, `spec-draft-n-max = 4`; **hermine** (RTX 4090, 23028 MiB, CUDA) `ctx-size = 65536`, KV `q8_0`/`q8_0`, `spec-draft-n-max = 3` — measured 2026-08-04 at 22467 MiB peak (~560 MiB free), 2391 t/s prompt / 86 t/s generation. Native max is 262144, but on hermine `llama-fit-params` caps a V-`q8_0` run at 58624 with its default 1 GiB margin; the KV cache is preallocated in full at load, so 65536 is a deliberate low-margin choice that assumes nothing else claims VRAM. Text+Image via optional `mmproj = …/mmproj-F16.gguf`. Vendor sampling: `temp 1.0`, `top-p 0.95`, `top-k 64`; thinking is opt-in via a `<|think|>` token → `jinja = true`. Two follow-ups from the 26B-A4B work were settled here by measurement on 2026-08-05, five real loads at ctx 65536: **`cache-type-k/v-draft` saves no VRAM at all** — 22265–22269 MiB at load and 22277–22281 MiB after generation, identical to within 4 MiB whether the draft cache is f16 or `q4_0`. The assumption behind adding it (a separate drafter cache sitting next to the target's) is wrong for MTP: the drafter shares the target's KV cache, which is what the 26B's card states outright. It is set to `q4_0` anyway because it costs nothing and generation was faster in all three `q4_0` runs (80.45 / 80.00 / 72.41 t/s) than in both f16 runs (66.90 / 69.20), tracking draft acceptance (0.849 / 0.849 / 0.727 against 0.656 / 0.684). **Do not quote a percentage**: an initial pair of bit-identical `q4_0` runs suggested a clean +16 %, and the third run landed between the two clusters, so n is too small and the spread too wide for anything beyond "not slower, probably a little faster". All five prompts were the same short one, so the prompt-throughput figures (133–169 t/s) are not comparable to the 2391 t/s above, which used a large prompt. `cache-reuse = 256` is **inert** here too — `cache_reuse is not supported by this context, it will be disabled` in 5 of 5 logs — which later turned out to be true of every model on this build, see the dedicated bullet below. `ctx-size` stays 65536, and a second attempt to improve it on 2026-08-05 also came back negative: with `fit = off` the section runs 77.3 t/s at 577 MiB free, 78.2 at 1540 (ctx 49152) and 78.1 at 2508 (ctx 32768) — **flat**, no CPU offload anywhere. Giving up context buys nothing here, so the thin margin is a robustness question only, not a speed one. This is also the measurement that killed the free-VRAM explanation for the Ornith-1.0-35B cliff.
